## Reading the ratios

- `wall/process CPU/alloc ratio ≈ 1.0` → consume-side overhead negligible on that workload
- `consumer CPU p50` tracks session-owned thread ids (`jfr-metrics-consumer` + EventStream ids born after pre-start mark); sampler refreshes last CPU on a nominal 1ms sleep
- Limits: poll gaps follow `Thread.sleep(1)` + scheduling (not a hard 1ms error bound); mid-measure EventStream replacements are re-adopted around the flush-cover window, not every poll; identity is appearance-after-mark
- Enabled legs fail fast if no live EventStream worker is owned after attach; sampler blocks on a latch until process/sampler CPU baselines are taken together
- `wall` ratios use **workload-only** wall (flush-cover wait is excluded from wall, still included in consumer/process CPU sampling)
- Sampler work is refresh-only (equal baseline/enabled poll cost); sampler CPU is subtracted from process CPU
- Accepted pairs with enabled-first order: `16/36`
- `alloc` is measured inside the workload (per-worker `getCurrentThreadAllocatedBytes`), not via live-thread snapshots
- `dropped` / `keys` are Micrometer gauges after the scenario’s last enabled leg
- Short GC Δ noise is normal; prefer wall/CPU/alloc ratios across scenarios
