## Reading the ratios

- `wall/process CPU/alloc ratio ≈ 1.0` → consume-side overhead negligible on that workload
- `consumer CPU p50` tracks session-owned thread ids (`jfr-metrics-consumer` + EventStream ids born after pre-start mark); 1ms sampler retains last CPU if an owned thread exits mid-sample
- Limits: up to ~1ms of CPU after the last poll before an owned thread exits may be missed; EventStream worker identity is not a public JDK API (appearance-after-mark)
- Sampler records its own CPU before exit and that delta is subtracted from process CPU on both legs
- Accepted pairs with enabled-first order: `16/36`
- `alloc` is measured inside the workload (per-worker `getCurrentThreadAllocatedBytes`), not via live-thread snapshots
- `dropped` / `keys` are Micrometer gauges after the scenario’s last enabled leg
- Short GC Δ noise is normal; prefer wall/CPU/alloc ratios across scenarios
